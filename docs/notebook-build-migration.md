# Notebook local build evidence

The imported browser test pinned the historical core SHA-256 `be423962e3a889e792a69a1ab60b978bcbf5ae1102db74a68c70a9a1c65e5942`. That attestation is historical and does not qualify this migrated build. The first local build produced `7b113527cb1507ce569fb92fb56d661c302cbfb663e3d164fbe439149ed27280`. The causes of this difference are isolated in the last section of this page; binary equivalence is not asserted.

The browser test now compares actual HTTP bytes with the shipping manifest and its hashed qualification manifest. The latter records current source and recipe hashes, pinned Node identity, observed Rust version, closed WIT and zero core imports. Existing successful restoration, authentication refusals, invalid-envelope refusals, interrupted staging and secret-clearing assertions remain unchanged. These are local tests, not deployment or universal runtime qualification.

## Why the migrated core fingerprint differs from the historical one

Measured on 2026-10-09 with the Notebook harness transpile chain (`componentNew` then `transpileBytes`, `@bytecodealliance/jco-transpile` 0.4.2, options identical to `tools/qualification/notebook-core-v2/build.ts`), Rust 1.97.0, `wasm32-unknown-unknown`.

Reference: the archived hub tree at commit `176aa32` (2026-07-17, the product-host fault campaign that pins it), built at an unrelated path with its own `Cargo.lock` and root manifest, yields transpiled core `be423962…5942`, the historical pin. The historical fingerprint is therefore reproducible; it is the migrated build that moved. Recovery commit `05b0533` (2026-09-17) changed two independent inputs:

1. The root manifest lost its `[profile.release]` block (`lto = true`, `codegen-units = 1`, `strip = true`, `panic = "abort"`). Without it the core module is 466,950 bytes instead of 359,714 and keeps a `name` section whose private symbol suffixes (`.llvm.<hash>`) follow the checkout path: the same commit built at three paths gave three different fingerprints, with every code and data section byte-identical and only the `name` section differing. This is the compiler/path contribution that the first paragraph of this page said had not been isolated; the first local build `7b113527…` is consistent with an unstripped build at another checkout path (not reproduced: its path is unknown). The profile is restored in `Cargo.toml`; with it the fingerprint no longer depends on the checkout path (two paths, identical hashes).
2. The locked dependency graph of the core moved: `argon2` 0.5.3 to 0.6.0 (with `digest` 0.10 to 0.11 and `blake2` 0.10 to 0.11, plus `cmov` and `ctutils`), `serde`/`serde_core`/`serde_derive` 1.0.228 to 1.0.229, `serde_json` 1.0.150 to 1.0.151, `wit-bindgen` 0.59.0 to 0.61.1 and `wit-component`/`wit-parser`/`wasmparser`/`wasm-encoder` 0.253.0 to 0.258.0. This changes the compiled bytes, so the historical hash cannot come back without reverting these pins.

With the profile restored the migrated build is core module `828938c8…0995`, transpiled core `f0455527…5d60`, bindings `ced45517…b0d1` (the bindings did not change).

## Machine paths in the build (owner decision Y40, 2026-10-09)

Before the remap, the module embedded the absolute `CARGO_HOME` registry path of every dependency panic location (19 strings, each starting with the builder's home directory), so the builder's user name shipped inside `notebook-core.core.wasm` (19 strings in the core module, the component and the transpiled core alike), and the same commit gave core module `828938c8…` on macOS arm64 but `31ad3728…` on the Linux composition runner.

`trim-paths` is not stable in Cargo 1.97.0 and `build.ts` rejects external Rust flags, so the remap is part of the audited recipe itself. `build.ts` derives the prefixes from the build environment (`scripts/machine-paths.ts`) and passes them to both WASM builds (product and `qualification-faults`) as `cargo --config target.wasm32-unknown-unknown.rustflags=[…]`; cargo appends `--config` arrays to the `+simd128` flags of `.cargo/config.toml`, which stays unchanged and remains the only SIMD configuration. The targets are fixed strings, in rustc's last-match order: `$HOME` → `~`, repository root → `.`, `$RUSTUP_HOME` → `/rustup`, `$CARGO_HOME` → `/cargo` (real-path variants included). The external-control refusal list is unchanged.

The recipe then scans every module, component and generated file it wrote for `/Users/`, `/home/`, `.cargo/registry`, `.rustup` and the builder's own `HOME`, `CARGO_HOME`, `RUSTUP_HOME` and repository root, prints the volume examined and fails on any hit or on an empty or unreadable file. The qualification manifest records `pathRemap` (the targets and the scanned volume, never the remapped prefixes) and lists `scripts/machine-paths.ts` among the build inputs. `bun run check:artifact-paths` (part of `check`) applies the same remap and scan to the `p02-worker` release binary.

The fingerprint no longer depends on the user, the home directory or the checkout path: two local paths and the hosted macOS runner give the same bytes. It still depends on the build host's operating system and architecture: a Linux arm64 container build of the same commit gives `e87a1739…37a8`, a third value, with no machine path in any of them and an identical size (359,458 bytes). The disassembled modules differ in function order and data offsets. The crate metadata hashes cargo assigns differ across hosts for crates downstream of host-compiled code (`serde_json`, `argon2`) and match for a crate without such dependencies (`base64`); the per-host `-C metadata` is consistent with that ordering change. Making the bytes host independent needs controls that stable Cargo 1.97.0 does not offer; the qualified fingerprint is therefore a per-host value (the campaigns run on macOS arm64).

Golden vectors replayed on the migrated dependency graph, against the pinned contracts authority fixture (`sha256` `734eeece…ee09`, identical to the fixture of the hub at `176aa32`): `cargo test --locked -p libre-ai-notebook-core` passes 21 tests (10 unit, 11 golden), covering the Argon2id derivation, AES-256-GCM, the canonical envelope, the ten backup refusals and the twelve Context refusals. This shows behavioural equivalence on the public vectors; it is not a binary equivalence claim and does not re-run the browser, process-fault and storage campaigns.

`QUALIFIED_CORE_SHA256` in `product-host-faults.playwright.ts` and `product-host-storage.playwright.ts` still holds the historical value on purpose. Those campaigns therefore refuse the migrated build until it is either re-pinned after the campaigns have been replayed on the pinned hardware, or the dependency pins listed above are reverted. That decision is the owner's; the pin is not adjusted to match the build. The remap changes the shipped bytes again: the value measured for the shipped `notebook-core.core.wasm` on macOS arm64 is the transpiled core `7498c60c…046c` above, recorded here as a measurement, not as a qualification (owner decision Y41: the campaigns are replayed on the pinned Node, browsers and hardware before any re-pin).
